## Origin

`HANDOFF.md` step 4 told the next session to set `OMR_SERVICE_URL` to "the VM's
address". No such address existed: the service bound `127.0.0.1:8000`, and the
host had no nginx, no certificate, no domain, and no systemd unit. This was a
step missing from the plan rather than a step left undone — merging #41 and #42
could never have made production upload work on its own.

## The decision

Plain HTTP without TLS, for the test phase only, chosen by the user. D-012
records it, and records what it accepts rather than only what it achieves: the
shared secret crosses the internet in the clear, so an on-path observer can
capture it, spend up to fifteen minutes of a two-vCPU box per `/process` call,
and read any observed job's score from `/result`.

`omr/auth.py` argues that "the exposure worth controlling is an unauthenticated
caller, not an eavesdropper". That is true only while the secret arrives safely.
D-012 exists so that comment is not read as unconditional once plaintext removes
its premise.

**What makes the trade defensible is ordering.** D-011 had already removed the
credential that mattered from this host — verified 2026-08-23 by inspecting the
running container's environment for any `SUPABASE`/`SERVICE_ROLE` variable and
finding none. Plaintext therefore exposes the secret, the PDF and the animation
JSON, but never `SUPABASE_SERVICE_ROLE_KEY`. The same choice taken before D-011
would not have been defensible, and the entry says so rather than leaving the
reader to assume the decision was always this cheap.

An exit condition is recorded with the decision, because a temporary decision
without one becomes permanent by default. It was checked, not assumed:
`101.79.16.73.sslip.io` resolves to the host with no registration (`dig`,
2026-08-23), and ports 80 and 443 are already open in the ACG. Adding nginx
changes one line of the unit and one Vercel variable, and no application code.

## Choices worth not re-deriving

| Choice | Reason |
|---|---|
| Port 3000 | 8000 is not open in the ACG; 80/443 are kept free so the TLS upgrade needs no container change |
| Secret in `/etc/clairkeys-omr.env` (600) | `podman generate systemd --new` embeds the whole `podman run` line in a 644 unit file, so `-e SECRET=…` would publish it to every local user |
| systemd unit at all | Without one a reboot drops the service; per PR #41 that then fails every in-flight row |
| Image tagged by commit **and** `:current` | The unit references `:current`; the commit tag keeps a running image traceable to a merged commit |

## Verification at `3a3f35c`

Everything below ran **from a different machine over the public IP**. A check
against `127.0.0.1` proves nothing about whether Vercel can reach the host.

| Check | Result |
|---|---|
| `GET /health`, no token | 200 |
| `POST /process`, no token | 401 |
| `POST /process`, wrong token | 401 |
| `GET /status/{id}`, no token | 401 |
| Full conversion, Bach WTK1 Prelude 1 | `completed`, **514 notes**, 45,598 bytes |
| `/result` fetch over the internet | 0.051 s |
| User-supplied title | Survives; not overwritten by the service echo |
| Unit file contains the secret | No |
| `systemctl is-enabled` | `enabled`, `default.target` → `multi-user.target` |
| `systemctl restart` | Service recovers |
| Image rebuilt from merged `main` | Digest `2304d56eae3d` — byte-identical to the image verified at `dcc946a` |
| `npx jest` | 46 suites / 421 tests, 0 failures |

`200` on `/health` with `401` on everything else is the pair that matters: it
shows the host is reachable **and** the gate is on. Either alone is ambiguous.

514 notes matches every run since 2026-08-21, so the deployment did not change
the conversion.

## Not verified

- **No reboot.** Boot-time start is inferred from `enabled` plus a successful
  `systemctl restart`, not observed. The next person on the VM should reboot it
  once and confirm.
- **No Vercel-originated request.** The two variables are the user's to set, and
  they must be set together — `omrAuthHeaders()` returns `{}` without the secret,
  so a correct URL alone produces 401s that read as a service fault.
- Recognition accuracy, as always, is untouched: 514 is a count, not a
  correctness claim.
