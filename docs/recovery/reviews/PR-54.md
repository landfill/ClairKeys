## 왜 생겼나 — 사용자의 지적

2026-08-24, PR #53 병합 직후 사용자가 지적했다: "전일 작업한 OCR은 단순히 메트로놈 표기
숫자를 인식해서 악보에 반영하는 것인데, 제목/작곡자는 사용자가 입력하는 값이다. 리드미를
잘못 수정한 것 아닌가."

**두 지적 중 하나는 맞고 하나는 사실과 반대였다.** 둘 다 코드로 확인했다.

### 맞는 지적 — 제목·작곡가는 사용자 입력이다

| 표시 위치 | 출처 |
|---|---|
| `src/app/sheet/[id]/page.tsx:173,190` | **DB `SheetMusic` 행** = 사용자 입력 |
| `src/components/animation/AnimationPlayer.tsx:330,333` | 애니메이션 JSON의 `title`/`composer` |

폴링 라우트는 서비스 echo로 DB 행을 덮어쓰지 않는다. 그러므로 악보에서 유래한 값이
표면화될 수 있는 곳은 **플레이어 헤더 하나뿐**이고, 그 JSON을 만드는 `_extract_metadata`는
`<work-title>`·`<creator>`를 찾는데 그 둘은 Audiveris 출력에서 관측된 적이 없다
(PR #53에서 이미 열린 질문으로 기록).

결론: **OCR 복구(#49)가 사용자에게 보이는 무언가를 바꿨다는 증거는 아직 없다.** PR #53은
이 사실을 `<credit-words>` 실측 뒤에 각주처럼 두었고, 그래서 OCR이 실제보다 커 보였다.
이 PR이 절의 첫 문단으로 끌어올린다.

### 사실과 반대인 지적 — OCR 작업은 메트로놈 인식이 아니었다

`gh pr view --json files`로 확인한 실제 변경 범위:

| PR | 파일 | 정체 |
|---|---|---|
| #50 | `omr-service/Dockerfile.audiveris`, `tests/test_audiveris_runtime.py` | **OCR 전반** (traineddata 교체). 메트로놈 관련 코드 없음 |
| #51 | `converter.py`, `app.py`, `OMRUploadForm.tsx`, 계약 타입·픽스처 14종 | **빠르기 계약**. OCR 아님 |

그리고 OCR을 되살린 뒤에도 같은 악보에서 `<metronome>`은 **0개**였다
(`validation/2026-08-23-omr-image-rebuild-after-48-49.md`). 인쇄된 메트로놈 표기는 지금도
인식되지 않으며, **PR #51이 업로드 폼에 빠르기 입력 필드를 넣은 이유가 정확히 그것이다.**
현재 재생되는 빠르기는 `tempoSource: "user"` 또는 `"unknown"`이고, `"score"`는 실제 악보에서
한 번도 관측된 적이 없다.

이 오해가 생기는 것 자체가 문서의 결함이므로, 두 PR이 각각 무엇이었는지를 README 본문에
명시했다.

## 변경 내용

- OCR 절 첫머리에 "지금 OCR이 제품에 기여하는 바는 확인된 것이 없다" 소절 신설. 표시 경로
  두 개(DB 행 / 애니메이션 JSON)를 파일명과 함께 명시
- 메트로놈 절에 #50·#51의 실제 범위 구분 추가
- 빠르기 문단에 현재 `tempoSource`가 `user`/`unknown`뿐이라는 사실 명시
- topology 다이어그램 OCR 노드 라벨 `제목 · 작곡가 · 마디 번호` → `지면의 글자`
  (앞 라벨은 그 값들이 제품에 반영된다는 인상을 준다)

## 검증

문서 전용. 표시 경로를 코드에서 직접 추적했고, PR #50·#51 파일 목록을 GitHub API로 확인했다.

검증하지 못한 것: Audiveris가 `<work-title>`을 내보내는지. 이 PR은 그 질문을 각주에서 절의
중심으로 끌어올릴 뿐 답하지 않는다.
