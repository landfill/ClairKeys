## What the inventory established

Only `/api/omr/upload` converts a score. `/api/upload-async`, `/api/processing`, and `/api/upload`
all reach `pdfParser.createEnhancedDemo()`, which picks a canned melody by file length and never
opens the PDF, then write it as an ordinary `SheetMusic` row with no marker. D-001 has forbidden
this since 2026-07-19; the code never followed it. `/api/upload` has zero product callers.

Full evidence: `docs/recovery/validation/2026-07-25-p1a-upload-path-inventory.md`.

## The consequence the PR asks the user to accept

After stages 3–5, **uploading will visibly fail until issue #22 is fixed** — the canonical path
cannot run Audiveris on a Docker-less host. This is the end of a concealment rather than a
regression: the demo paths currently make a broken converter look like a working one, which is what
D-001 exists to prevent. Recorded explicitly in D-010 under `Consequence`.

## Review round 1 — 2 findings, both valid, both fixed in `da8e121`

**Codex (P2) — D-010 claimed stage 2 without the migration plan stage 2 requires.** Valid, and
chasing it corrected an error in D-010's own text. D-010 said the demo paths leave no
distinguishing field; that holds for intent but not for recoverability. **No demo writer sets
`omrJobId`; only `/api/omr/upload` does.** A failed OMR request leaves `animationDataUrl` empty, so
`omrJobId IS NULL AND animationDataUrl <> ''` names exactly the fabricated rows, with D-009's Shape
A outlier as a cross-check on the stored JSON. Decision 5 now specifies:

- Identify with a read-only script, run once under user approval, recorded in `validation/`.
- **Mark rather than delete** — new `provenance` column (`'omr' | 'demo' | 'unknown'`). Those rows
  hold user-chosen titles, categories, and `PracticeSession` history, and a misjudged row cannot be
  restored. Deleting stays the user's individual call.
- Disclose on the playback screen; exclude from `/api/sheet/public`. This carries D-001's "must
  return a demo state" down into the data layer.
- Clients: `/api/upload` has zero callers so nothing needs transition; `/api/upload-async` and
  `/api/processing` keep their path and progress contract and lose only persistence, so stage 3 must
  update `MultiStageUploadUI` / `BackgroundFileUpload` error handling.
- The migration ships in its own PR **after** the writers close — counting rows while demo rows
  still arrive measures nothing.

**CodeRabbit (Minor) — `/api/upload` missing from the persistence test.** Valid; that route writes
its own `SheetMusic` row. The loop now covers all three writers, and a new test pins the `omrJobId`
asymmetry so a later change cannot quietly destroy the identifier the migration depends on.
