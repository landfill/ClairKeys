## Origin

D-011 was decided with the user on 2026-08-21 and recorded in HANDOFF, but had
no code and no `DECISIONS.md` entry. This PR is both.

The fact it rests on: `omr/storage.py` uploaded with `SUPABASE_ANON_KEY`, and
Storage RLS rejects that key with 403. The service could never have stored
anything; being undeployed is the only reason nobody saw it.

## The design question, and why it went the way it did

The reflexive repair is to give the service `SUPABASE_SERVICE_ROLE_KEY`. That
key bypasses RLS across the whole project, and the host would be a public-IP VM
with SELinux `Disabled` and firewalld `inactive`. The upload therefore moved to
the Next.js side, which already holds that key on Vercel, and the service now
holds no credential at all.

The secondary decisions all follow from how the route is called:

- The payload is on `GET /result/{job_id}`, not `/status`, because `/status` is
  polled in a loop.
- The store is keyed on the job id with `upsert`, because two polls can observe
  the same completed job at once. A random filename would produce two objects
  and orphan whichever lost the race to the database row.
- `title`/`composer` are no longer copied back from the service. Before PR #38
  that echo was the PDF's filename — the second link in the concealment chain.

## Shared secret

`/process`, `/status`, and `/result` require `X-ClairKeys-Token`; `/health`
stays open for nginx and uptime checks. An unset `OMR_SHARED_SECRET` makes the
service refuse **every** request rather than run unauthenticated, with
`ENVIRONMENT=development` the only exception — the same fail-closed shape as the
local-fallback guard it replaces.

`omr/auth.py` imports stdlib only, with the FastAPI wiring left in `app.py`.
That is deliberate: `omr-service/tests` runs in an environment without fastapi,
so a check that imported it could only be asserted from an AST. It is the same
property that made the deleted `storage.py` testable for real.

## Correction carried by this PR

`[]` recorded on 2026-08-21 was the anon key lacking permission to list buckets.
D-011's premise is therefore confirmed rather than assumed.

## Not verified

- Nothing here has run against a live OMR service or a real Supabase upload.
- The 30 s `/result` timeout has not been measured against a real score.
- The in-memory payload's lifetime across a service restart is unexercised —
  a restart between completion and collection fails the row, which is correct
  but untested.
- `omr-service/tests/*.py` still runs in no CI workflow, so the Python half of
  this evidence protects nothing automatically. The Next.js tests do run.
