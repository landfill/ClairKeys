## Why this shape

Two of the three items are perceptual and the tests cannot judge them, so the loop had been
change-constant → deploy → listen → repeat. The volume control breaks that loop: its numeric readout
is the master gain value, so the level that sounds right is read straight off as the number to set as
`DEFAULT_MASTER_GAIN`. The user proposed exactly this — tune live, confirm the default from the
observed value.

Loudness is corrected at the gain stage, not by changing normalisation. `harmonicAmplitudes` stays
normalised to sum 1 (the tests pin it, and `disableNormalization: true` depends on it), and a sum-1
series has lower RMS than the old unit sine — so the fix is a louder bus, bounded by the same
clipping-headroom argument as the default: a note peaks near `PEAK_GAIN`, up to `VOICE_LIMIT` voices
overlap, so `MAX_MASTER_GAIN` caps the drag.

## CodeRabbit round and merge

CodeRabbit reviewed `a8a933f` and raised **four valid findings**, all fixed in `de67c5c`:

1. **Dishonest clamp (Minor, real bug).** `setVolume` clamped the bus but the player stored the raw
   request, so dragging past the ceiling showed a readout the bus was not at — defeating the control's
   whole purpose. `setVolume` now returns the applied value and the player stores that.
2. **No real headroom (P2).** `MAX_MASTER_GAIN` was 0.6; a voice peaks near 0.3 and up to 24 overlap,
   so 0.6 could clip a dense passage. Lowered to 0.35, and the slider max now reads the constant.
3. **Slider behaviour untested (Major).** Added a component test asserting the readout is the gain
   value and a change forwards to `setVolume`.
4. **Treble tuning unpinned (Major).** Added a `pianoTimbre` test fixing C6's fundamental share
   (~0.78) so `TREBLE_ROLLOFF` cannot silently drift back to 2.4.

Merged per the user's "merge now" decision after CI passed on `de67c5c`: all required checks green,
