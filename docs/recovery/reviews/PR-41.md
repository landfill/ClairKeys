## Origin

The user reported on 2026-08-23 that uploading sheet music in **production**
(`clairkeys.vercel.app`) created a database row, returned `Internal server
error`, and stored no file.

All three symptoms trace to one fact already recorded in HANDOFF: the OMR
service has never been deployed anywhere, and `OMR_SERVICE_URL` still named
`https://clairkeys-omr.fly.dev`. Confirmed live:

```
$ curl -sS -m 15 https://clairkeys-omr.fly.dev/health
curl: (35) schannel: failed to receive handshake, SSL/TLS connection failed
```

Fly's wildcard DNS resolves the name, so the request reaches TLS and `fetch`
**throws**. A thrown `fetch` is not a non-ok response, so it skipped the
`!omrResponse.ok` branch — which would have said "Failed to start OMR
processing" — and fell into the outer `catch`, whose message is exactly the
`Internal server error` the user quoted. Storage never ran because storage was
the OMR service's step.

## The defect this PR fixes

The `catch` branch never marked the created row `failed`. The row stayed at
`processing` with no `omrJobId`, and `/api/omr/status/[jobId]` looks rows up by
`omrJobId` — so nothing could ever move it again. One permanent orphan per
upload attempt.

## What it deliberately does not do

It does not make upload succeed. D-010 accepted that upload fails visibly until
issue #22 lands. No demo generator, no fallback, no nicer message presented as a
fix. The failure is now honest about *which* failure it is.

## Incidental finding, recorded because it corrects the record

`animation-data` **exists**. A service-role probe of `GET /storage/v1/bucket`
returned all three buckets (`sheet-music-files`, `temp-uploads`,
`animation-data`; the last is public, 10 MB limit, `application/json` only). The
`[]` recorded on 2026-08-21 was the anon key lacking permission to list buckets,
not a missing bucket. This removes a risk from the D-011 work: the service-role
upload path has a bucket to write to.

## Second commit `1750ec5` — the same stranded row, reached from the other side

Added 2026-08-23 at the user's direction, after the VM verification of PR #42
found it. It belongs here rather than in #42 because removing the stranded row
is what this PR is for; #42 only happened to be the run that exposed the second
route into it.

The upload route reached that state by creating a row before a `fetch` that
threw. The status route reaches it from the other side: it looks rows up by
`omrJobId`, and it returned 502 for **every** non-ok status without writing
anything. A row it could not resolve stayed at `processing` while every later
poll took the identical path to the identical 502.

What turned this from theory into a measurement is the live service. Job state
is held in memory, so after `podman restart` the same job answers **404** on
both `/status` and `/result` — observed on the VM on 2026-08-23. The host has no
systemd unit, so a reboot does this to every in-flight job at once.

The fix is a single distinction the route never drew:

- **"I cannot reach the service"** — transient. The `catch` branch above already
  gets this right by deliberately leaving the stored status alone. 5xx, 401, and
  503 belong with it: a failing service, a shared secret that does not match
  yet, one not set at all. An operator fixes those and the same job resumes, so
  failing the row would destroy recoverable work.
- **"the service answered, and this job is gone"** — permanent. Only a 404 means
  this, and only 404 now fails the row.

The 404 response is `200` with `status: 'failed'`, not an error status. The
poller in `OMRProcessingStatus.tsx:72-74` throws on any non-ok response and
reports a generic "failed to check status"; answering 200 puts it on the branch
it already has for a service-reported failure, which carries a message the user
can act on.

A 404 from `/result` after `/status` said `completed` is not separately handled,
and does not need to be: it requires a restart between two calls in one
invocation, and the next poll's `/status` 404 fails the row through the path
above.
