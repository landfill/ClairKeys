## Origin

The user asked for a detailed architecture diagram in the README, with the
option of filing it as an issue if the timing was wrong. The timing was right:
the end-to-end path had run for the first time hours earlier, so the shape of
the system was first-hand rather than reconstructed. Drawing it later would have
meant reassembling it from PRs #41/#42/#43 and decisions D-009 through D-012.

## Three diagrams, because one was doing two jobs badly

The first attempt was a single `flowchart LR` carrying both topology and
per-call labels. It rendered, and it was unreadable: two edges leaving
`/api/omr/upload` — one creating the database row, one calling `/process` —
both appeared to terminate at the OMR service, so the diagram could not answer
the question it existed to answer.

Split into: a topology chart answering only "what runs where and which
credential crosses which boundary", and two sequence diagrams carrying call
detail. **This was caught by rendering the diagram and looking at it**, not by
reading the source, which is the only way it could have been caught.

## Credentials on the boundaries

Deliberate. That the VM holds no storage credential is the one fact that
explains most of the architecture — why the service returns JSON rather than
storing it (D-011), why the browser fetches from Storage directly, and why plain
HTTP to the VM was an acceptable test-phase trade (D-012). A reader who takes in
only the first diagram should still leave with it.

## CodeRabbit review — the first complete one in this sequence

Worth noting on its own: PRs #41 and #42 never got a full review (`Review limit
reached`, then `Review rate limited`). This PR did — `Review completed`, two
inline findings, **both valid**. Rated Major; verified against the code before
acting, and the substance held even where the framing did not.

### 1. "The OMR service holds no credentials" was wrong as written

`omr/auth.py:39` reads `OMR_SHARED_SECRET`, and an unset value makes the service
refuse every request with 503. A reader following that table would have deployed
a service nobody can call.

Fixed by splitting one column into two: what must be **configured**, and what can
be used to **reach something else**. The service needs the secret to verify
callers and cannot go anywhere with it; `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS
across the project. That distinction *is* D-011 — collapsing it into "없음" lost
the reason while overstating the result.

### 2. The failure table contradicted itself, because it was two routes

It said a connection failure both fails the row and preserves the stored state.
Both were true, of different routes:

| Route | `catch` behaviour |
|---|---|
| `upload/route.ts` | `markFailed(sheetMusic.id)` — row becomes `failed` |
| `status/[jobId]/route.ts` | returns 503, writes nothing |

The table now carries a 시점 column and the rows are separate.

CodeRabbit suggested reserving `failed` for permanent failures. That is already
the policy during polling, and must **not** be the policy at upload — the README
now says why. At upload the row has no `omrJobId`, so a failed call leaves no job
to resume; not failing it strands the row permanently, which is the defect PR #41
was opened to remove. During polling the row has an `omrJobId` and work may still
be running, so failing it destroys recoverable work. Only 404 fails a row during
polling, because only 404 means the job is gone.

Same exception, opposite handling, both correct. The README was wrong to flatten
it; the code was not.
