## 무엇을 왜

사용자 보고: "악보 재생 소리가 너무 웹오디오 한계처럼 삑삑거리는 수준 같다."

PR #30/#32/#33이 합성 음색을 세 번 귀로 튜닝했지만 전자음 인상이 남았다. 원인은
상수가 아니라 구조다 — `createNoteAudio`가 음 하나에 oscillator 1개와 gain 1개를
주므로 24개 배음이 하나의 엔벨로프를 공유하고 같은 속도로 죽는다. 실제 현은 상위
배음이 수백 ms 안에 사라지고 기음이 몇 초를 울린다. 어떤 rolloff 값으로도 그 차이는
나오지 않는다.

`AudioBufferSourceNode`가 `OscillatorNode`와 같은 `start(when)`/`stop(when)`을
제공하므로 변경이 `createNoteAudio` 안에 갇혔다. **PR #26의 클럭 앵커, 롤링
look-ahead, `VOICE_LIMIT`, seek 재발성 로직은 손대지 않았다.**

## 설계를 결정한 두 실측

- **메모리**: 원본 세트를 그대로 디코딩하면 **142MB**(스테레오 30개, 합계 422초).
  `scripts/build-piano-samples.sh`가 모노 변환 + 음역별 트림으로 120초 /
  **20.2MB** / 디스크 1.17MB로 만든다.
- **게인**: 빌드된 세트의 최대 피크는 A0의 -7.7 dBFS(선형 0.4112). 합성 경로의
  `PEAK_GAIN`은 0.3이므로 `SAMPLE_PEAK_GAIN = 0.73`으로 되맞췄다. 이게 없으면 첫
  화음이 약 37% 크게 나오고 `DEFAULT_MASTER_GAIN`·`MAX_MASTER_GAIN`의 헤드룸
  근거가 조용히 무효가 된다.

## 테스트가 아니라 브라우저 실측이 잡아낸 결함 2개

1. **도입부에서 악기가 바뀌었다.** 뱅크 로딩이 재생 클릭 시점의
   `initializeAudio`에서야 시작되므로 첫 음들이 합성음으로 났다(실측 샘플 5 : 합성
   3). `startAudio`가 뱅크를 기다리되 2.5초에서 끊는다.
2. **seek이 해머 타격음을 다시 재생했다.** `start(when)`은 버퍼를 0에서 다시
   시작한다. 합성 경로의 4ms 어택 뒤에서는 안 들렸고 녹음된 타격음에서는 들린다.
   경과 출력 시간을 playbackRate로 버퍼 오프셋으로 환산해 `start(when, offset)`로
   넘기고, 버퍼 길이로 clamp한다.

## 검증 기록

- 신규 테스트 32개: `pianoSamples` 12, `pianoSampleBank` 10, 재생 훅의 샘플 분기 10.
- **teardown 회귀 테스트 2개를 기존 oscillator 경로에 먼저 작성해 통과를 확인한 뒤**
  샘플 경로에서 다시 통과시켰다. 이 변경에서 가장 깨지기 쉬운 지점이 정지·탐색 시
  voice가 살아남는 것이었다.
- 헤드리스 Chromium으로 실행 중인 앱 검증: buffer source 8 / oscillator 0(대기
  수정 전에는 5 / 3), 음 게인이 정확히 `velocity × 0.73`, 콘솔 오류 없음.
- 브라우저 디코딩이 ffmpeg 상수를 확인: 30/30 디코딩, 모노 44.1kHz, 120.0초,
  20.2MB, 피크 0.4112 @ MIDI 21 (코드의 `SAMPLE_SET_PEAK`는 0.4111).
- `npm run build` 통과. `/samples/piano/60.mp3`가
  `public, max-age=31536000, immutable`로 서빙됨.

## CodeRabbit 리뷰 — actionable 1건, 처리 완료

`scripts/build-piano-samples.sh:89`의 `ffmpeg`가 `-nostdin` 없이
`echo "$SAMPLES" | while read` 루프 안에서 실행돼, ffmpeg가 파이프의 stdin을 소비하면
`read`가 다음 줄을 받지 못하고 루프가 조기 종료될 수 있었다(ShellCheck `SC2095`).

`6315a77`에서 `-nostdin`을 추가했다. 검증: shellcheck 0.11.0이 수정 전 `SC2095`를
**2건**(info + warning) 보고하고 수정 후 **0건**이며, `bash -n`도 통과한다.
스크립트를 재실행하지는 않았다 — 재실행은 커밋된 샘플을 다시 내려받아 재인코딩한다.

이 결함은 **동작한 실행이 루프의 건전성을 증명하지 않는** 형태다. PR에 샘플 30개가
전부 커밋돼 있어 실행한 머신에서는 완전한 세트가 나왔지만, 그것이 루프가 옳다는 근거는
아니다. 리뷰 스레드는 답신 후 resolved 처리했다.
