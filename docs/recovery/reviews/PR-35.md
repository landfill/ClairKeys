## Review round 1 — 1 finding, valid, fixed in `b578841`

**Codex (P2) — "Reject retries for permanently unavailable jobs".** Verified end to end:
`ProcessingDashboard` → `useBackgroundProcessing.retryJob` → `POST /api/processing/[jobId]`
(`action: 'retry'`) → `backgroundProcessor.retryJob`. That method resets the row to `PENDING` but
never restores `ProcessingJobData` to the in-memory `processingQueue`, so `processQueue` has nothing
to run and the job sits at 0% forever — **a visible failure replaced by a job that looks like it is
starting and never does**, which is worse than the failure it came from.

The latent defect predates this branch (a server restart could always leave a `FAILED` row with an
empty queue). What stages 3–5 changed is **frequency**: with no converter behind the path, every job
fails, so the retry button moved from an edge case to the normal case. That is a consequence of this
PR even though the bug is older, so it is fixed here.

`retryJob` now returns `false` when the recorded error starts with `CONVERSION_UNAVAILABLE`; the
route answers "Failed to retry job" and the dashboard keeps showing the original failure.
Re-enqueuing was the alternative and does not work — the uploaded file buffer is gone, so the job
would fail again with a less honest error.

Regression test added to `backgroundProcessor.test.ts`: it fails before the fix and passes after.
That suite's `pdfParser` mock was also removed, since `backgroundProcessor` no longer imports the
demo generator and a mock for it would imply otherwise.

A commit `Directive` records that this refusal should be revisited when P1-B makes the queue durable
— a retry that can actually re-run belongs to a converter that exists.
