## Scope

P1-A Work stages 3–5 — the behaviour change D-010 authorised, after the user approved D-010 and the
merge of PR #34 on 2026-07-25. One commit `889ec36`:

**Stage 3 — one path on the upload page.** `src/app/upload/page.tsx` loses the `백그라운드 처리`
and `즉시 처리` mode cards and the `uploadMode` state; only `OMRUploadForm` remains. The modes were
removed rather than relabelled: pointing them at endpoints that always fail would keep both broken
even after issue #22 restores the converter, and stage 3 asks for callers to *move* to the canonical
path.

**Stage 5 — deletions.** `src/app/api/upload/route.ts`, `src/hooks/useFileUpload.ts`, and
`src/hooks/__tests__/useFileUpload.test.ts` are gone. Zero product callers, and the route could still
write a fabricated score.

**Stage 4 — persistence removed from the two async paths.** `asyncUploadProcessor.processUpload` and
`backgroundProcessor.processJob` keep their signatures and the queue/notification contracts (P1-B
inherits the seam) but no longer write `SheetMusic` rows. Both return `CONVERSION_UNAVAILABLE` from
the new `src/services/conversionAvailability.ts`. Two deliberate details:

- `backgroundProcessor.processJob` **bypasses `handleJobError`**, which retries to `maxRetries`. No
  number of retries makes a converter appear.
- The 25 seconds of invented `omr` progress went with it. Showing progress for work that is not
  happening was the deception, not merely the storage.

**Stage 4 — `pdfParser` isolated, not deleted.** `assertDemoGenerationAllowed()` throws when
`NODE_ENV === 'production'`. It survives because without an OMR service there is no other way to
exercise playback locally, and its melodies must stay literal for D-010's migration to classify rows
already stored.

One import in `musicDataConverter.ts` became `import type`, so the module cannot invoke the
generator. It still sources its types there because the identically named types in
`src/types/piano.ts` have a **different shape** (`key` vs `note`) — reconciling them is P2-A's work.
