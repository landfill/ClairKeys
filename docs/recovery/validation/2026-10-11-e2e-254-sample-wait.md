trial 1의 진단 repeat 5는 이슈와 같은 `playback-play` viewport ratio 0 → element not found로 실패했다. click +263ms의 busy 프레임에서 버튼 rect `(176,334,80,48)`·scrollY=0·ratio=1을 확인한 뒤 다음 프레임은 +2627ms의 재생 시작이었다. 샘플 응답은 여전히 보류돼 있었지만 버튼은 DOM에서 제거되고 compact bar가 나타났다. 준비 문구·busy 단언은 통과한 다음 viewport 단언 도중 제거됐다(trace의 viewport 단언 224116.5 → 229143.7ms). repeat 7/9도 +2746/+2671ms에 대기 안내가 사라져 실패했다.

판정: 샘플 응답 보류만으로 준비 상태를 유지한다고 가정한 테스트의 시간 경쟁을 실제 Linux에서도 확인했다. 제품의 2500ms 상한 이후 fallback 재생은 정상 계약이다. 화면 밖 이동·회전의 증거는 없었다. 프레임 간 공백 때문에 모든 순간의 레이아웃을 증명한 것은 아니지만, 이슈와 같은 실패 경로에서 준비 상태 종료를 확인했다.

## 제어된 회귀와 수정

원본 spec으로부터 같은 probe를 생성해 busy 버튼의 실제 native IO ratio>0을 단언한 뒤 테스트 프로세스만 3000ms 늦췄다. 수정 전: `(176,334,80,48)`·busy=true·ratio=1 → 2999ms 뒤 버튼 제거·loading 없음·compact bar 있음 → 기존 viewport 단언 FAIL. 샘플 응답은 계속 보류됐다.

수정은 Playwright clock을 navigation 전에 설치하고, 사전 요청이 시작된 후 click 전에 멈춘다. 실제 loading 상태의 disabled 버튼을 확인한 poll만 250ms씩 진행시켜 200ms 안내를 표시한다(총 진행 1000ms 상한, 제품 2500ms 상한 미만). 화면 단언 뒤 샘플을 풀 때 시계를 다시 진행한다. 기존 5초 busy 판정·Firefox skip 조건·viewport 단언·재요청 없음·실제 재생 시작 확인은 유지한다. 제품 코드·대기 상한·retries·worker 수를 바꾸지 않는다.

같은 probe의 최종 수정 후: 호스트 3초 지연에도 준비 버튼·loading·ratio=1 유지, 샘플 release 후 정상 시작, 전체 단언 PASS (4.9초). 중간 버전은 안내 표시의 200ms timer를 진행하지 않아 busy 이전에 실패했고, 최종 poll로 바로잡았다. 이 실패를 숨기거나 기존 실패로 분류하지 않는다.

Clock 설치·pause/run/resume 순서는 [Playwright 공식 문서](https://playwright.dev/docs/clock)를 따른다. 가짜 시간·호스트 지연은 테스트 제어이며 제품 대기 시간을 늘린 것이 아니다. 최종 spec에는 실제 sleep이 없다. 기존 audio sample Jest가 timeout fallback 계약을 따로 고정한다.

수정 `e2a53a7`의 로컬 검증: `first-play-sample-loading.spec.ts`의 Chromium·Firefox·WebKit·Mobile Safari를 `--repeat-each=5 --workers=2 --retries=0`로 실행해 40 passed(49.7초), 전체 Jest 171 suites/1731 tests, `tsc --noEmit --incremental false`·lint 모두 PASS. 기존 실패·제외 증가 없음. Firefox는 이 macOS 환경에서 오디오를 시작해 skip이 없었고, Linux의 기존 no-audio skip은 PR CI에서 확인한다.
