# 2026-08-27 — 이슈 #63 마스터 게인 스테이징 재산정 검증

대상 브랜치: `codex/p1a-master-gain-staging`, 커밋 `fd22fa0`
기준 커밋: `6c232ce` (`DEFAULT_MASTER_GAIN = 0.22`, `MAX_MASTER_GAIN = 0.35`, 샘플 세트 `v1`)

## 증상과 최초 확인

사용자 보고: **음량 슬라이더 최대(0.35) + 기기 음량 최대에서도 소리가 작다.**

먼저 게인 체인에 숨은 감쇠 단계가 있는지 확인했다. `useFallingNotesAudio.ts`의 노드 연결을
전수 확인한 결과 `source → (lowpass) → voiceGain → masterGain → destination` 외에 감쇠 지점은
없다. 즉 체인은 지시받은 대로 동작하고 있으며 값 자체가 낮다.

| 상황 | 최종 피크 |
|---|---|
| 단음, 슬라이더 최대 | **−22.5 dBFS** |
| 조밀 8음 화음, 슬라이더 최대 | **−10.5 dBFS** |
| 조밀 8음 화음, 기본값 | **−14.5 dBFS** |

일반 음원의 피크는 −1 ~ −3 dBFS다.

## 측정 — 실제 믹스다운 렌더

기존 게인이 근거로 삼은 **보이스 선형 합산**이 실제와 얼마나 다른지 확인하기 위해, 추정이 아니라
실제 오디오를 합성해 쟀다.

- 샘플 경로: `public/samples/piano/*.mp3`를 `afconvert`로 디코딩한 실제 버퍼를 사용. 최근접 샘플
  선택과 `playbackRate` 리샘플링(선형 보간)을 실제 스케줄러와 동일하게 적용
- 합성 경로: `pianoTimbre`가 순수 함수이므로 스케줄러가 만드는 그대로 렌더 — 사인 위상
  `PeriodicWave`, `timbreCutoffHz`의 Web Audio lowpass biquad(Q=1), attack/지수감쇠/release 엔벨로프
- 양쪽 모두 velocity **0.7** (`converter.py`가 velocity를 내보내지 않으므로 실제 재생 값)

### 결과 — 선형 모델은 2~4배 비관적이다

| 시나리오 | 샘플 실측 피크 | 선형합 대비 | 합성 실측 피크 |
|---|---|---|---|
| 단음 C4 | 0.278 | — | 0.135 |
| 3화음 C-E-G | 0.683 | 107% | — |
| 양손 5음 | 0.667 | **62%** | — |
| 조밀 8음 | 0.853 | **50%** | 0.940 |
| 페달 12음 누적 | 0.642 | **25%** | — |
| 동시타 12음 | 1.082 | 42% | 1.086 |
| 동시타 16음 | 1.231 | 36% | 1.356 |

### 직관이 뒤집히는 지점

**페달로 누적된 12음(0.642)이 동시타 8음(0.853)보다 피크가 낮다.** 온셋이 어긋나 트랜지언트가
겹치지 않기 때문이다. 즉 "보이스가 많을수록 위험하다"가 단조롭게 성립하지 않으므로, 보이스 수로
상한을 잡는 방식 자체가 오디오가 묻지 않는 질문에 답하고 있었다.

### 두 경로가 3 dB 이내다

조밀 8음에서 샘플 0.853 대 합성 0.940. **D-015의 라우드니스 정합이 실제로 작동했다는 방증**이며,
동시에 상한을 **합성 기준**으로 잡아야 하는 이유다(버스 공유, 합성이 더 크다).

## 선택한 값과 그 검산

`DEFAULT_MASTER_GAIN` 0.22 → **0.7**, `MAX_MASTER_GAIN` 0.35 → **0.9**.

| 시나리오 | 샘플 × 0.9 | 합성 × 0.9 | 판정 |
|---|---|---|---|
| 조밀 8음 | 0.768 (−2.3 dBFS) | 0.846 (−1.5 dBFS) | 안전 |
| 페달 12음 | 0.578 (−4.8 dBFS) | — | 안전 |
| 동시타 12음 | 0.974 (−0.2 dBFS) | 0.977 (−0.2 dBFS) | 안전(경계) |

기본값 0.7에서 조밀 8음은 −4.5 dBFS다.

동시타 16음은 열 손가락으로 도달 불가능하며, 이를 상한 기준으로 삼는 것이 바로 이 결함을 만든
실수이므로 **바깥 경계로만 기록**한다.

## 제거한 테스트

PR #62가 추가한 `keeps a dense chord clear of the clip point at both master levels`를
**제거했다.** 그 테스트는 `보이스 수 × 세트 최대 피크`로 클리핑을 검사했으므로, 이 작업이
폐기하는 모델을 그대로 고정하고 있었다. 새 값에서 실패하는 것이 정상이며, **완화가 아니라
대체**다 — 클리핑 검증은 실측 믹스다운 기반 `master gain staging` 블록이 이어받는다.

## 검증하지 못한 것

- **소리를 아무도 듣지 않았다.** PR #59·#62와 같은 제약이며 청감 확인은 운영 배포 후에만 가능하다.
- 병리적인 악보가 실제로 동시 16보이스에 도달할 수 있는지 확인하지 않았다. `VOICE_LIMIT`가 24이므로
  구조적으로는 가능하다.
- 브라우저에서의 실제 출력 레벨은 측정하지 않았다. 오프라인 렌더가 Web Audio의 합산과 동일하다고
  가정했다(선형 합산이므로 타당하나 실측은 아니다).
