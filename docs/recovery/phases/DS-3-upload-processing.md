## Objective

업로드를 "파일을 던지고 기다리는 화면"에서 "지금 무엇이 일어나고 있고 얼마나 걸리는지 아는 화면"으로
바꾼다. 이 단계의 문구는 전부 **DS-G1이 확정한 상태 출처**에 근거해야 한다 — 없는 데이터를 전제로
화면을 그리지 않는다 (D-024 결정 5).

## In scope

- PDF 선택 / 파일 검사 / 변환 요청을 서로 다른 상태로 표시
- 대형 드롭존, PDF 조건, 예시 악보와 지원 범위 안내
- 잘못된 파일·암호화 PDF·용량 초과·중복 파일 상태
- 제출 전 예상 처리 시간과 백그라운드 처리 안내 (DS0-7)
- 처리 중 화면: **아래 4단계 표현**, `이 페이지를 닫아도 계속 처리됩니다` 고정 노출,
  `다른 악보 둘러보기`·`내 악보로 이동`
- 실패 화면: **아래 실패 4종**의 문구와 복구 행동. Java 스택 트레이스 비노출 (이슈 #47)

### 확정된 계약 (D-026)

**처리 단계는 업로드 화면에서만 표시한다.** 그 화면만 `jobId`를 갖고 서버는 단계를 저장하지 않는다.

| OMR `progress` | 화면 문구 |
|---:|---|
| 0 | 대기 중 |
| 10 | PDF 분석 |
| 30 | 음표 인식 |
| 60 | 연주 데이터 생성 |
| 100 | 학습 화면 준비 |

**사용자 대면 실패 4종:**

| 유형 | 발생 지점 | 복구 행동 |
|---|---|---|
| 파일 거부 | 업로드 전 클라이언트 검증 | 파일을 고쳐 다시 선택 |
| 변환 실패 | Audiveris가 악보를 읽지 못함 (이슈 #46 포함) | 더 선명한 PDF로 재시도 |
| 작업 유실 | OMR 재시작으로 job 소실 (`/status` 404) | 다시 업로드 (한국어 문구 기존재) |
| 서비스 불가 | OMR 도달 불가 (503) | 잠시 후 재시도. **저장된 상태를 바꾸지 않는다** |

## Out of scope

- 내 악보 목록의 상태 표시 (DS-4). 같은 계약을 읽지만 화면이 다르다
- 완료 알림과 전역 진입점 (DS-7)
- OMR 서비스·백엔드 변경. 이 단계는 UI다. **예외 하나**: `/api/omr/status/[jobId]`의 404 분기에
  실패 종류를 가를 `code`를 더한다 (D-028). 그 응답과 변환 실패 응답이 구분되지 않으면 실패 4종
  계약을 화면에서 지킬 수 없다. 저장 동작과 HTTP 상태는 그대로다
- 저해상도 PDF 인식 실패의 근본 해결 (이슈 #46). 사용자 대면 문구만 다룬다

## 회귀 기준

**기능 회귀**

- canonical 업로드 경로가 `/api/omr/upload` 하나로 유지된다 (D-010). 새 업로드 경로를 만들지 않는다.
- 페이지를 떠나도 완료 저장이 이뤄진다 (D-018 callback). 폴링 fallback을 제거하지 않는다.
- 빠르기(BPM) 선택 입력과 "비워두면 빠르기 미상" 동작이 유지된다 (D-013, 이슈 #82).
- 업로드 성공 시 생성되는 행의 `provenance`가 `omr`이다 (P1-A).

**시각 회귀**

- DS-1 토큰만 사용한다. 새 색상 리터럴을 도입하지 않는다.

## 2026-08-30 D-032 주 — 업로드 한도가 50MB에서 4.5MB로 바뀌었다

이 단계는 "최대 50MB"를 화면에 고정했지만, 그 한도는 Vercel Function의 요청 본문 한도 4.5MB와
충돌했다(이월 항목 DS3-1). 5MB PDF는 화면의 모든 검사를 통과한 뒤 플랫폼이 413으로 끊었고, 그
413이 "잠시 후 재시도"로 분류돼 성공할 수 없는 재시도를 권했다.

사용자 지시로 한도를 낮췄다 — 처음 4.5MB(D-032), 이어서 여유를 둬 **4MB**(D-033). 숫자는
`MAX_UPLOAD_BYTES` 한 곳에서 오고 화면 문구·서버 검사·테스트가 전부 그것을 파생한다. 이 단계의
완료 조건과 Progress 기록에 남은 "50MB"는 DS-3 완료 시점의 사실이다.

여유를 둔 이유는 오버헤드(약 2KB)가 아니라 **MB 해석 차이(218,592바이트)** 다. 플랫폼 문서의
`4.5MB`가 십진이면 4,500,000이고, 이진으로 읽은 4,718,592는 그것을 이미 넘는다. 4MB는 두 해석
모두에서 안전하다.

**남은 것**: `uploadFailures.ts`에 `status === 413` 분기가 없는 것은 그대로다. 다만 크기 때문에
413에 도달하는 경로는 사실상 없어졌고, 남는 413은 예외적 상황이다.

## 반응형 검증

- 데스크톱 1440·1024, 모바일 390 세로에서 드롭존과 안내가 한 화면에 들어온다.

## Completion criteria

- 업로드 화면에 **예상 처리 시간**과 **백그라운드 처리 안내**가 제출 전에 보인다.
- 처리 중 화면에 `이 페이지를 닫아도 계속 처리됩니다`가 고정 노출된다.
- 처리 단계 표시가 위 `progress` 매핑만 사용한다. **서버가 모르는 구간을 아는 것처럼 표현하지
  않는다.** 업로드 화면을 떠난 뒤의 화면에는 단계를 노출하지 않는다 (D-026 G1-2).
- 실패 4종 각각이 서로 다른 문구와 복구 행동을 갖는다.
- OMR 503일 때 저장된 `processingStatus`가 바뀌지 않는다 (회귀 테스트).
- 잘못된 파일·용량 초과·암호화 PDF 각각에 대해 사용자가 취할 행동이 화면에 있다 (실패 4종 중
  '파일 거부').
- 실패 화면에 스택 트레이스가 노출되지 않는다 (실패 fixture로 회귀 테스트).
- 버튼·안내 문구에 `OMR` 같은 기술 용어가 없다.
- 각 상태(선택 전 / 검사 중 / 요청됨 / 처리 중 / 완료 / 실패)의 회귀 테스트가 있다.

## 완료 판정 (2026-08-29)

phase 완료 조건 10개를 모두 충족했다. 근거는
`docs/recovery/validation/2026-08-29-DS-3-upload-processing.md`.

**다만 이슈 #76 완료 조건 4는 이 단계가 판정하지 못했다.** 그 조건의 판정 방법은 "실제 업로드
1회"인데, 로컬에 DB도 OMR 서비스도 없어 실행하지 못했다. 화면이 예상 대기 시간과 처리 단계를
보여준다는 것은 회귀 테스트와 로컬 실제 브라우저(API를 가로챈 상태)로 확인했지만, **운영
파이프라인을 한 번 통과시킨 증거는 없다.** 조건 5(이탈 안내 고정 노출)는 관측으로 충족했다.
DS-7이 종단 판정할 때 이 항목을 실제 업로드로 채워야 한다.
